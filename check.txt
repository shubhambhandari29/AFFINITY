Latest master notes:
**Subject: SAC Loss Run Integration – Delivered Functionality, Production Readiness and DB Team Requirements**

Hi [Manager’s Name],

We have integrated SAC loss-run generation into the SAC application. This brings report generation, scheduling, monitoring and downloads into a single application-managed flow, replacing the need to run the existing standalone scripts separately.

Below is a summary of the functionality implemented, the impact on the current process, and the preparation required for production.

### 1. Functionality implemented

**On-demand report generation**

Users can generate either a **Standard Loss Run** or a **Claim Review** report for:

- One selected account.
- Multiple selected accounts.
- All eligible accounts.

The account-selection screen displays customer details, onboarding date, account status and loss-run frequency. Both active and inactive accounts are supported. Eligibility is driven by the configured Loss Run Distribution Frequency rather than requiring the account to be active.

**Extended-history reporting**

Users can optionally select a loss-date starting point through the calendar. This supports requests for older history, including dates going back to 2004 or earlier, subject to the data available in our databases.

When no date is selected, the existing default reporting rules remain applicable: the current/prior-six-policy-year rule for closed claims, together with open claims and claims with positive outstanding loss reserves.

The extended-history option is implemented, but complete agreement with OBIEE’s historical reports remains dependent on source-data availability and financial reconciliation.

**Background processing and job tracking**

Report generation can take several minutes, particularly when retrieving claims and financial data. We changed this from a long-running browser request to a database-backed background job.

The application now:

- Accepts a request and returns a job ID promptly.
- Processes the report through a background worker.
- Displays queued, processing, completed, partially completed, failed and cancelled states.
- Shows the processing phase, requested/processed/generated/failed account counts, timestamps and failure details.
- Retains job history, displayed newest first.
- Prevents a second manual generation request from starting while another job is queued or processing.

This addresses the gateway timeouts previously encountered in Azure while report generation continued in the background.

**Cancellation and downloads**

Users can cancel queued or running jobs. Running jobs request cancellation of the active SQL operation or stop at a safe processing boundary. Files already generated remain available.

Generated Excel files continue to be stored in Databricks. Users can also download the generated files through the application, packaged as a ZIP where applicable.

**Report content and presentation**

We have implemented:

- Template-based generation for Standard and Claim Review workbooks.
- Reports for eligible accounts with no claims, retaining the cover page and displaying a no-claims message.
- Account-specific review thresholds using `tblAcctSpecial.CRThresh`.
- Claim-level threshold calculations combining loss reserve and paid loss across exposures, excluding expenses, with equality included.
- Threshold filters on the relevant summary/review sheets, without displaying the threshold on the cover page.
- Standard-report summary grouping, newest-policy-year-first ordering and annual subtotals.
- A combination chart showing claim counts and total incurred, with straight line segments and value labels.
- Formatting improvements to match the client’s monthly burst-report presentation.
- Corrections for Excel repair issues encountered during testing.

### 2. Automatic monthly generation

The application supports the existing monthly schedule:

| Date | Report |
|---|---|
| 1st of each month | Standard Loss Run |
| 20th of each month | Claim Review |

Both are scheduled for **12:00 AM US Eastern time**, following daylight-saving changes through the `America/New_York` timezone.

The scheduler creates jobs for all eligible accounts, and the same background worker processes both scheduled and manually requested jobs. Scheduled work waits when another job is active. Schedule occurrences are recorded to prevent duplicate scheduling, and missed occurrences since the activation date can be picked up after a restart.

The current scope is **generation, storage and download—not automatic email distribution**.

### 3. Database changes required in production

The following application-owned tables must be deployed in **`CLMAA_SpecialAccounts`**:

| Table | Purpose |
|---|---|
| `dbo.tblLossRunJob` | Stores job requests, report options, status, progress counts, timestamps, cancellation state and worker/recovery information |
| `dbo.tblLossRunJobAccount` | Stores account-level processing results, generated-file paths and errors |
| `dbo.tblLossRunSchedule` | Stores monthly schedule definitions, report types, timezone, activation date and enablement |

The production deployment must include the **latest complete schema**, including changes added after the original table creation—for example, report type, selected loss date, scheduling metadata, cancellation flag, worker lease/heartbeat and retry fields. Related keys, indexes, defaults and constraints must also be included.

For scheduling, we need two production schedule records: the 1st for Standard and the 20th for Claim Review. The agreed activation date should be set carefully to avoid unintended historical catch-up runs.

The existing report view, **`dbo.SAC_Loss_Run`**, must also be aligned with the approved version, including support for inactive accounts. Extended-history retrieval currently uses an application-owned SQL file; it does not require creating a second view. The deployed database objects and application query path should be reviewed together before release.

### 4. Data Engineering / DB team preparation

We will need the team’s support with the following:

**Access and permissions**

- Grant the production application’s managed identity the necessary access to `CLMAA_SpecialAccounts` and the referenced `CLM_LakeHouse` objects.
- Provide read access to report-source objects and the required read/write access to the new job and schedule tables.
- Validate cross-database access using the application identity, not only a developer’s SSMS login.
- Confirm any required execution permissions if a stored-procedure-based retrieval path is adopted.

**Filtered financial-table loading**

The reports currently use:

- `CLMAA_SpecialAccounts.dbo.DW_FINCL_LOSS_FTR_SS_F_FILTERED`
- `CLMAA_SpecialAccounts.dbo.DW_FINCL_LOSS_TXN_SS_F_FILTERED`

During PREPROD testing, financial records for inactive accounts were missing from these filtered tables, although matching records existed in LakeHouse. We performed a controlled PREPROD backfill for the identified inactive accounts, with audit records and rollback scripts.

For production, we need the team to confirm:

- Which process populates these filtered tables.
- Its account-selection rules, historical coverage and financial transformations.
- Whether inactive accounts are included.
- How an approved historical backfill and ongoing refresh should be handled.

The experimental PREPROD backfill should **not be treated as an approved production migration** without this review.

### 5. Other production prerequisites

Alongside the DB changes, we need:

- Production Databricks workspace/catalog configuration.
- Managed-identity access to read the templates and read/write generated reports, including the necessary Unity Catalog permissions.
- Both approved Excel templates in the production template location.
- An approved production output location—the current code uses a directory named `specialaccounts_lossruns_temporary`, which should be reviewed before go-live.
- Validation that the background worker remains operational across application restarts, with appropriate monitoring and ownership.
- End-to-end testing of manual generation, monthly schedules, cancellation, partial failures and downloads.

### 6. Outstanding validation

The application functionality is implemented and has been exercised in local/PREPROD environments, but **financial reconciliation is not yet complete**.

The latest Aubuchon comparison identified a query defect where historical litigation statuses can split an exposure into multiple rows, and an expense fallback can repeat an exposure-level expense total. A candidate correction needs to be validated against both inactive and active accounts before changing the shared production query.

Separately, some LakeHouse financial amounts and claim populations differ from OBIEE’s reports. Our Mansermar comparison also showed that, although most common exposures reconcile closely, the reports do not match completely. These source-data and calculation differences require resolution or explicit business acceptance before financial sign-off.

### 7. Impact on the existing process and cutover

The intended future flow is:

**Manual request or monthly schedule → SAC job queue → background generation → Databricks storage → application status and download**

This replaces the separate execution mechanism currently used outside the SAC application for the 1st/20th monthly runs. It adds user-controlled generation, visibility, cancellation and downloads within SAC.

Once production validation and business sign-off are complete, we should coordinate a cutover date and **disable/retire the equivalent standalone schedules and scripts** to avoid duplicate generation. Before retirement, we should confirm that those scripts have no additional downstream responsibilities—such as distribution or other outputs—outside the replacement scope.

In summary, SAC now contains the report-generation and scheduling capabilities needed to take ownership of this process. The remaining production work is to deploy the supporting database/storage setup, resolve the financial-data/query validation items, and complete a controlled cutover from the existing standalone process.
